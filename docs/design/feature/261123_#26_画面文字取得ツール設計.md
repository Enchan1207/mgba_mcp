# get_screenに付加する画面文字情報の設計

## 1. 目的と対象範囲

[issue #26「ゲーム画面に表示されている文字情報の取得方法を調査する」](https://github.com/Enchan1207/mgba_mcp/issues/26)で確認したWRAMの画面用タイル列を復号し、既存のMCPツール`get_screen`の結果に文字情報を付加する機能を定義する。独立した`get_screen_text`ツールは公開しない。最初の対応対象は日本版『ポケットモンスター 赤』の初期版と1.1版とする。

日本語の文字コード表は1つのアセットにまとめる。ゲームと版の識別にはカートリッジヘッダを使う。画面用タイル列は実行時に`mgba_server`から取得する。

## 2. 検証済みの根拠

- 稼働中の日本版『赤』初期版では、`READ C3A0 360`で取得した20列×18行のタイル列から開始メニューと会話欄の表示文字を復元できた。濁点と半濁点は文字の一行上、同じ列のタイルから合成した。[実ROMでの検証結果](https://github.com/Enchan1207/mgba_mcp/issues/26#issuecomment-7089133729)
- [日本版『赤・緑』のビルド設定](https://github.com/Narishma-gb/pokegreen/blob/master/Makefile)は初期版のROMバージョンを`0`、1.1版を`1`に設定する。両版は同じ[日本語charmap](https://github.com/Narishma-gb/pokegreen/blob/master/constants/charmap.asm)を参照する。
- [初期版のシンボル表](https://github.com/Narishma-gb/pokegreen/blob/symbols/pokered.sym)と[1.1版のシンボル表](https://github.com/Narishma-gb/pokegreen/blob/symbols/pokered11.sym)では、`wTileMap=C3A0`、`wMenuCursorLocation=CC30`、`wStringBuffer=CF45`、`wNamingScreenNameLength=CEE4`、`wAlphabetCase=CEE6`が一致する。
- 文字コード表には同じタイル番号を共有する文字がある。また、画面ごとに読み込む図柄が同じ番号を使う。例えば`CD`は「へ」と「ヘ」、`F0`は通常フォントの「円」と名前入力画面の終了図柄に使われる。文字表の単純な全画面適用では、図柄を文字と誤認する。

## 3. ROMの識別

文字取得featureは注入されたメモリ読み出し関数を使い、`READ 0134 28`に相当する操作でヘッダの`0134`から`014F`を取得する。[カートリッジヘッダ仕様](https://github.com/gbdev/pandocs/blob/master/src/The_Cartridge_Header.md)に従い、タイトル、リージョン、ROMバージョン、ヘッダチェックサムを検証する。

| 項目 | アドレス | 対応値 |
| --- | --- | --- |
| タイトル | `0134`～`0143` | `POKEMON RED`と残りのゼロ埋め |
| リージョン | `014A` | `00` |
| ROMバージョン | `014C` | 初期版は`00`、1.1版は`01` |
| ヘッダチェックサム | `014D` | `0134`～`014C`から計算した値 |

一致したヘッダから`pokemon_red_jp_rev0`または`pokemon_red_jp_rev1`を選ぶ。対応しないヘッダでは復号を実行せず、文字取得featureは未対応を返す。`get_screen`自体は画像を返す。ヘッダは画面取得ごとに読み、サーバの再起動後も古い判定を使わない。

ヘッダの値を保った改造ROMは同じプロファイルとして判定される。この対応範囲を超える厳密な同一性確認が必要になった場合は、`mgba_server`が起動時に計算したROM全体のハッシュを公開する。

## 4. アセットと責務

`mgba_server`は従来どおり`CAPTURE`と`READ`コマンドを提供し、画面文字の解釈を行わない。MCPの`get_screen`は既存の`CAPTURE`処理で画像を取得し、文字情報は別のfeatureで生成してMCP contentに追加する。

### 4.1 ディレクトリと責務の境界

MCP側のコードを次の責務で分類する。

| ディレクトリ | 責務 |
| --- | --- |
| `mcp/src/tools/` | MCPツールの公開定義・入出力スキーマと、必要な処理の組み立て。既存の`features/tools/`はここへ移動する |
| `mcp/src/features/` | 対象ゲームの内部仕様・意味を理解するドメイン機能。MCPツールとは独立して利用・テストできる |
| `mcp/src/lib/` | ゲーム固有の知識を持たない汎用ロジック。既存の`image-encoder`はここに維持する |
| `mcp/src/external/` | `mgba_server`など外部システムとの通信・プロトコルの実装 |

構成例は以下のとおり。

```text
mcp/src/
  external/mgba-client/
  features/game-state/read-screen-text/
  lib/image-encoder/
  lib/mcp-tools/
  tools/
    get-screen/
    press-button/
    run-input-batch/
    walk-for/
    wait/
    index.ts
```

`tools`から`features`、`lib`、`external`を利用できる。`features`は`tools`や`external`に直接依存せず、外部操作が必要なら関数として注入する。`lib`はゲーム固有の仕様やMCPツール定義を知らない。

すべてのツールに対応するfeatureを作る必要はない。`press_button`、`walk_for`など、対象ゲームの内部仕様を解釈しない単純なコマンドの組み立ては`tools`内で完結させる。機能を使う箇所が一つでも、ゲーム固有の知識を持つ`read-screen-text`は`features`に分離する。

PNGエンコードはドメイン知識を要しない画像変換のため`lib/image-encoder`に残す。画像取得処理を薄いfeatureで包むことはしない。画像をMCP contentに整形する処理を複数ツールで共有する必要が生じた場合は、`tools`配下の共通処理として抽出する。

### 4.2 文字取得featureとツールの接続



文字取得featureは`mcp/src/features/game-state/read-screen-text/`に配置する。ゲーム固有のcharmap（LUT）と濁点・半濁点の変換表、およびROMヘッダの判定条件を保持する。初期版と1.1版では同じ文字表・`wTileMap`アドレスを使用する。

featureには「指定アドレスから指定長のバイト列を読む」関数だけを注入する。`external/mgba-client`、MCP SDK、CONTROLコマンド、ソケット、操作キューには直接依存させない。概念的なシグネチャは以下とする。

```ts
type ReadMemory = (address: number, length: number) => Promise<Uint8Array>
type ScreenTextData = { lines: { y: number; text: string }[] }

// effect -> (input -> text_data) の構成。
// 今回は実行時入力がないため、生成した関数は引数なしで呼ぶ。
function createReadScreenText(readMemory: ReadMemory):
  () => Promise<ScreenTextData | undefined>
```

`undefined`は未対応ROMを表す。通信エラーや読み取り失敗を未対応扱いに変換しない。具体的なエラー型および命名は実装時に既存コードの規約に合わせる。

`get_screen`側は`run-with-mgba-client`の操作内で`client.send({ verb: 'read', args: [address, length] })`を呼ぶアダプタを作り、読み出したバイト列を返す関数としてfeatureに注入する。`CAPTURE`自体の実装は既存のコマンド経路を維持する。feature内ではコマンド送信や接続管理を行わない。

## 5. 文字の復号

1. ヘッダを読み、対応ROMかを判定する。
2. 対応ROMであれば`wTileMap=C3A0`から360バイト（20列×18行）を読む。
3. 256要素のLUTで、各タイルを代表文字に変換する。非文字タイル・枠線・カーソル記号・未定義タイルは空白にする。同じタイル番号を共有する「へ／ヘ」「り／リ」などは代表文字一つに固定し、候補は返さない。
4. 上の行の同じ列に濁点（`E5`）または半濁点（`E4`）があれば、下の文字に明示的な対応表を適用して合成する。合成できた場合は濁点・半濁点の元の位置を空白にする。合成できない場合は誤変換しない。Unicode正規化には依存しない。
5. 各行を左から右へ連結する。文字が一つもない行は除外し、残った行を画面上の行番号`y`（0〜17）とともに返す。行内の空白は省略・圧縮せず、20タイル分の位置を維持する。

結果は`{ lines: { y, text }[] }`とし、複数行を会話やメニューなどの意味的な領域にまとめない。各行の全文字が空白ならその行は除外してよいが、行内のスペースは保持する。画面の種類、ウィンドウ、意味上のカーソル位置、選択中の文字・項目は推定しない。

同一タイル番号が画面専用の絵柄で上書きされる場合など、LUTと実表示が一致しないことがある。この機能はベストエフォートの文字情報として扱い、ゲーム状態の解析による補正は行わない。

## 6. get_screenへの統合

既存のMCPツール`get_screen`に、従来の画像contentとステータス情報に加えて、文字情報のtext contentを追加する。例えば次のような形式である。

```text
Screen text (tile coordinates; y is 0-based):
y=14: " ポケット モンスターの"
y=16: " ようこそ！"
```

文字情報の行は画像と照らし合わせるための補助情報であり、画面種別や文字の属するウィンドウは判定しない。新たな独立MCPツールは登録しない。`get_screen`の既存画像形式、`framesAdvanced`および`totalFrames`は維持する。文字情報はまずtext contentとして付加し、既存`structuredContent`の互換性を崩さない。

画面画像は既存の`captureScreen`で取得する。`NO_FRAME`時に1フレーム進めて再取得する既存動作は維持し、その後の停止状態で文字情報を読む。文字取得自体は`STEP`やボタン操作を行わない。両方の取得は同一の`run-with-mgba-client`操作内で行い、別のMCP操作が途中に割り込まないようにする。

未対応ROMの場合は文字contentを省略して画像のみ返す。文字取得中の通信・復号エラーを未対応ROMとして隠蔽しない。エラーを`get_screen`全体の失敗として伝えるか、画像とともに補足エラーを返すかは、既存ツールのエラー方針に合わせて実装時に定める。

## 7. 検証方針

- 日本版『赤』初期版と1.1版をヘッダで識別し、未対応ROMでは画像のみ返す。
- `read-screen-text`は注入した読み出し関数のモックで単体テストする。読み出しアドレスと長さ（`0134`から28バイト、`C3A0`から360バイト）、復号結果を検証する。
- 濁点・半濁点が下の文字へ適用されること、適用不能な組み合わせを誤変換しないこと、代表文字と非文字タイルの空白化を検証する。
- 複数ウィンドウ・メニュー・会話・名前入力の各画面について、縦方向のグルーピングをせず、行番号と横方向の空白が保持されることを確認する。
- `get_screen`の画像content、ステータス、`NO_FRAME`時の従来動作を維持し、対応ROMでは文字contentが追加されることを確認する。
- 文字取得でフレームと入力状態が変化しないこと、画像取得と読み出しの間に別のMCP操作が割り込まないことを確認する。
