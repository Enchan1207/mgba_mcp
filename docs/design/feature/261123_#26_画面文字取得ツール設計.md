# 画面文字取得ツールの設計

## 1. 目的と対象範囲

[issue #26「ゲーム画面に表示されている文字情報の取得方法を調査する」](https://github.com/Enchan1207/mgba_mcp/issues/26)で確認したWRAMの画面用タイル列を使い、表示中の文字を構造化して返すMCPツールを定義する。最初の対応対象は日本版『ポケットモンスター 赤』の初期版と1.1版とする。

日本語の文字コード表は1つのアセットにまとめる。ゲームと版の識別にはカートリッジヘッダを使う。画面用タイル列は実行時に`mgba_server`から取得する。

## 2. 検証済みの根拠

- 稼働中の日本版『赤』初期版では、`READ C3A0 360`で取得した20列×18行のタイル列から開始メニューと会話欄の表示文字を復元できた。濁点と半濁点は文字の一行上、同じ列のタイルから合成した。[実ROMでの検証結果](https://github.com/Enchan1207/mgba_mcp/issues/26#issuecomment-7089133729)
- [日本版『赤・緑』のビルド設定](https://github.com/Narishma-gb/pokegreen/blob/master/Makefile)は初期版のROMバージョンを`0`、1.1版を`1`に設定する。両版は同じ[日本語charmap](https://github.com/Narishma-gb/pokegreen/blob/master/constants/charmap.asm)を参照する。
- [初期版のシンボル表](https://github.com/Narishma-gb/pokegreen/blob/symbols/pokered.sym)と[1.1版のシンボル表](https://github.com/Narishma-gb/pokegreen/blob/symbols/pokered11.sym)では、`wTileMap=C3A0`、`wMenuCursorLocation=CC30`、`wStringBuffer=CF45`、`wNamingScreenNameLength=CEE4`、`wAlphabetCase=CEE6`が一致する。
- 文字コード表には同じタイル番号を共有する文字がある。また、画面ごとに読み込む図柄が同じ番号を使う。例えば`CD`は「へ」と「ヘ」、`F0`は通常フォントの「円」と名前入力画面の終了図柄に使われる。文字表の単純な全画面適用では、図柄を文字と誤認する。

## 3. ROMの識別

ツールは`READ 0134 28`でヘッダの`0134`から`014F`を取得する。[カートリッジヘッダ仕様](https://github.com/gbdev/pandocs/blob/master/src/The_Cartridge_Header.md)に従い、タイトル、リージョン、ROMバージョン、ヘッダチェックサムを検証する。

| 項目 | アドレス | 対応値 |
| --- | --- | --- |
| タイトル | `0134`～`0143` | `POKEMON RED`と残りのゼロ埋め |
| リージョン | `014A` | `00` |
| ROMバージョン | `014C` | 初期版は`00`、1.1版は`01` |
| ヘッダチェックサム | `014D` | `0134`～`014C`から計算した値 |

一致したヘッダから`pokemon_red_jp_rev0`または`pokemon_red_jp_rev1`を選ぶ。対応しないヘッダでは復号を実行せず、対象外のROMであることをエラーとして返す。ヘッダは各ツール呼び出しで読み、サーバの再起動後も古い判定を使わない。

ヘッダの値を保った改造ROMは同じプロファイルとして判定される。この対応範囲を超える厳密な同一性確認が必要になった場合は、`mgba_server`が起動時に計算したROM全体のハッシュを公開する。

## 4. アセットと責務

`mgba_mcp`に日本語版の文字コード表を1ファイルで持つ。通常フォントの文字、濁点・半濁点、枠線、カーソル、画面固有の図柄、同じ番号を共有する文字の候補を表す。ROMの版ごとに文字表を複製しない。

ゲーム固有のプロファイルにはヘッダ識別条件、WRAMアドレス、文字コード表とタイルの分類規則を持たせる。初期版と1.1版で一致するアドレスは共通定義を参照する。画面の種類や会話・選択肢といった意味的な領域の判定規則は持たせない。将来、別の版で差が確認された場合はプロファイルでアドレスを切り替える。

`mgba_server`は既存の`READ`で生のバイト列を返す。MCP側はヘッダ識別、タイルの復号・分類、座標を保持した結果の整形を担当する。既存の`src/external/mgba-client`には`READ`のコマンドと応答の解析があるため、ツールから同じ通信経路を使う。

画面が会話欄、選択メニュー、名前入力画面のどれに当たるか、どの文字が選択肢や入力候補かといった文脈依存の解釈は、画面画像も参照できる呼び出し元エージェントに委ねる。

## 5. 公開ツール

`get_screen_text`は入力を持たず、ゲームを進めずに現在の画面用タイル列を復号・分類して返す。ひとつの`run-with-mgba-client`操作内でヘッダ、`wTileMap`、`STATUS`を順に取得する。`STATUS`の`hasFrame`が`false`なら`NO_FRAME`として終了し、フレームを進めない。

返却する観測情報は以下とする。

| 項目 | 内容 |
| --- | --- |
| `profile` | 判定したゲームと版 |
| `totalFrames` | 取得時の累積フレーム数 |
| `rows` | 上から順に18行。それぞれ20列のタイルに対応するセル情報を保持する。配列位置または明示的な座標から元の行・列を復元できる |
| `cursor`（任意） | 矢印等の既知のカーソル表示位置を確実に特定できる場合のみ、その行・列を返す。どの項目・文字を選択しているかまでは推定しない |

各セルでは少なくとも元のタイル値と、復号できた文字・記号の種別または未解決状態を表現する。複数の意味があるタイルは候補を列挙し、特定の画面を仮定して一つに確定しない。未解決の値も座標と元の値を失わず返す。既知の枠線やカーソルは文字として偽装せず、記号として分類する。濁点・半濁点は同じ列の上の行と照合し、合成された表示文字を表せるようにする。このとき元のタイル値と位置も保持する。

`rows`の具体的なシリアライズ形式は実装時に定める。ただし20×18の配置を再構築できること、文字と記号と不明値を区別できること、曖昧な候補を失わないことを必須とする。空白や枠線を削除して文字列だけを詰め直してはならない。

`screenKind`および意味的な文字領域を示す`regions`は返さない。未知の画面でも可能な限りタイルを復号し、画面の分類に失敗したことを理由にテキスト取得を断念しない。

カーソルについては、画面に現れる既知の矢印タイルと、必要に応じて`wMenuCursorLocation`を照合する。名前入力画面の`wStringBuffer`など用途を兼ねる作業領域は、画面の意味を確定せずに解釈すると誤認しうるため、このツールの必須出力には含めない。入力中文字列や選択文字の構造化が必要になれば、別の高水準機能として検討する。

## 6. 検証方針

- ヘッダのタイトル、リージョン、版、チェックサムを検証し、初期版と1.1版を識別する。対応外のROMは復号しない。
- 同じ文字表で初期版と1.1版のタイルを復号する。
- 会話の文字送り前後、開始メニューの選択移動、名前入力と文字種切替で画面と結果を照合する。画面種別の事前判定を行わず、それぞれの文字・記号が取得できるか確認する。
- 濁点・半濁点、同じ番号を共有する文字、画面固有の図柄、文字領域外のグラフィックについて、元のタイル値・座標・候補が維持されるか確認する。
- カーソル表示が確認できる場面では座標を照合し、確定できない場合は`cursor`を省略する。
- ツール実行後のフレーム数と入力状態が実行前から変化しないことを確認する。
