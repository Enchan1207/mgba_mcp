# MCPサーバのアーキテクチャを再編する

## 1. 目的と対象範囲

現在の`src/server.ts`にはMCPサーバの生成、`press_button`の定義、操作の直列化が混在している。`src/index.ts`は実行入口を担っており、サーバ定義の所在も分かりにくい。サーバ構成、実行入口、個別ツール、CONTROL通信の責務を分け、ツールを追加するときに既存ツールや標準入出力の処理を変更せずに済む構成を作る。

対象は`mgba_mcp`の内部アーキテクチャとする。既存の`src/index.ts`、`src/server.ts`、`src/control.ts`の内部構造は引き継がず、必要な責務に合わせて作り直す。`src/lib/socket-reader`は指定長のバイト列を順に読む部品として使用する。実装は必要に応じて作り直す。

公開ツールの名前、入力、戻り値、コマンド変換は[MCPサーバで提供する機能の設計](261113_%233_MCPサーバの提供機能を設計.md)に従う。`mgba_server`との通信形式は[コマンドリファレンス](../../server/command_references.md)に従う。この文書では、ツールを実行する各部品の責務と連携方法を定める。

## 2. 全体構成

`mgba_mcp`は標準入出力でMCP要求を受け、Unix domain socket上の1本の`CONTROL`接続を通じて`mgba_server`にコマンドを送る。起動時に設定を検証してMCPの受信を始める。ソケットへの接続は最初のゲーム操作まで遅らせる。

| 構成要素 | 責務 |
| --- | --- |
| `handler.ts` | 設定の検証、CONTROL接続と操作キューの生成、`serveStdio`の起動、終了時の片付け |
| `index.ts` | `createMcpServer(connection)`によるMCPサーバの生成とツールの登録 |
| `control.ts` | ソケット接続、CONTROL要求と応答、タイムアウト、接続状態の管理 |
| `lib/operation-queue` | 非同期操作の直列実行と、終了時の待機操作の解消 |
| `lib/socket-reader` | 分割受信したバイト列から指定長を読み、余剰バイトを次の読み取りへ持ち越す |
| `lib/tool` | SDKから独立したツール定義、ファクトリ、実行結果の型 |
| `features/tools/<brief>` | 個別ツールの入力定義とCONTROLコマンドの組み立て |

`src`の配置は次のとおりとする。

```text
src/
  index.ts
  handler.ts
  control.ts
  lib/
    operation-queue/
      index.ts
    socket-reader/
      index.ts
    tool/
      index.ts
  features/
    tools/
      press-button/
        index.ts
```

CONTROL応答はコマンドの種類によらず`src/lib/socket-reader`で読み取る。画像の解析は、指定長だけ読み取った`CAPTURE`の本文に対して行う。

## 3. 内部インターフェース

### 3.1 MCPサーバファクトリ

`src/index.ts`は`createMcpServer(connection): McpServer`を公開する。引数にはコマンド送信と操作の直列実行を提供するオブジェクトを渡す。ファクトリは個別ツールの定義を読み込み、実行コールバックに共通の操作キューを適用してから`registerTool`で登録する。環境変数の読み込み、ソケットの生成、標準入出力の起動は扱わない。

`src/handler.ts`はCONTROL接続と`src/lib/operation-queue`のキューを生成し、`createMcpServer`へ渡すオブジェクトを組み立てる。`serveStdio`には`createMcpServer(connection)`を呼ぶファクトリを渡す。`serveStdio`がMCPサーバを複数回生成しても、同じCONTROL接続と操作キューを共有する。

### 3.2 ツール定義

`src/lib/tool`はツールの名前、説明、入力スキーマ、必要な場合の出力スキーマ、実行コールバックを表す型を定義する。入力スキーマとコールバック引数の型の対応を保つ。個別ツールのファクトリはコマンド送信機能を受け取り、ツール定義を返す。

個別ツールにはコマンド送信機能だけを渡す。操作キューの取得や解放、中止制御用のコールバックは渡さない。MCP SDKの型は`src/index.ts`と`src/handler.ts`の境界で使用し、`lib/tool`と`features`以下では独自の型を使用する。SDKの公開用`Tool`型は実行コールバックを表さないため、内部のツール定義には使用しない。

### 3.3 CONTROL接続

`src/control.ts`はツールからコマンドを受け、一つのコマンドの応答を読み切ってから次のコマンドを送る。接続時には`HELLO CONTROL`の成功応答を確認してから通常のコマンドを受け付ける。どのコマンドでも、同じ`SocketReader`からヘッダー5バイト、ヘッダーに記載された長さの本文、終端1バイトを`readExactly`で順に読む。本文長と終端を検証し、異常な応答を受けた接続を破棄する。`CAPTURE`の本文は応答全体の読み取り後に画像形式として解析する。

接続層は操作の境界を識別する。通信が失敗した操作に属する後続コマンドを拒否し、次の操作が始まるまで再接続しない。この制約は共通の登録処理と接続層で実現する。

## 4. 操作の実行と並行処理

### 4.1 操作キュー

CONTROL応答には要求を識別するIDがない。複数のツールが同じ接続へ同時にコマンドを送り、それぞれ応答を読むと、応答を対応するコマンドへ確実に割り当てられない。そのため、ゲーム状態に触れる全ツールを一つの操作キューで直列化する。

キューはツールの実行コールバック全体を投入順に実行する。先行するツールの操作が完了するまで、次のツールを開始しない。これにより、複数コマンドから成る操作の途中に別のツールのコマンドが入らない。失敗した操作の後も後続の操作を実行する。

各MCP要求はキューに投入した操作の完了を待ち、結果またはエラーをその要求へ返す。`tools/list`などゲーム状態に触れないMCP要求は操作キューへ入れない。操作キューは`handler.ts`で生成するが、キューの処理は`src/lib/operation-queue`に置く。

### 4.2 標準入出力とソケット通信

使用中のMCP SDK 2.4.0では、`serveStdio`は標準入力の受信処理を登録して戻る。受信メッセージを順に振り分けるが、非同期ツールの完了を待って次のメッセージを処理する構造ではない。手元でも、完了を保留したツール要求の後に送った`tools/list`へ先に応答できることを確認した。[SDK 2.4.0の実装](https://github.com/modelcontextprotocol/typescript-sdk/blob/v2.4.0/packages/server/src/server/serveStdio.ts)

操作キューは専用スレッドを作らない。ソケットの書き込みや応答を`await`している間、Node.jsのイベントループは標準入力やソケットからの受信を処理できる。応答が届くと待機中の操作を再開し、完了後に次の操作を始める。同期的な長時間計算をツールに追加するとイベントループが止まるため、その処理時間を確認する。[Node.jsの非同期I/Oの説明](https://nodejs.org/learn/asynchronous-work/overview-of-blocking-vs-non-blocking)

## 5. 接続と障害時の扱い

### 5.1 接続とタイムアウト

`MGBA_MCP_SOCKET_PATH`は`handler.ts`が起動時に検証する。MCPの初期化ではソケットへ接続しない。最初のゲーム操作で接続を確立し、同時に複数のツールが要求されても接続を一つだけ保持する。接続確立とコマンド応答の待機時間には有限の上限を設ける。

### 5.2 操作途中の失敗

コマンドのエラー応答を受けた場合は、利用可能な接続に可能な範囲で`RELEASE ALL`を送ってから操作をエラーとして終了する。接続エラーや通信のタイムアウトが起きた場合はソケットを破棄し、操作を途中から再開しない。応答の対応関係が不明になった接続には追加のコマンドを送らない。再接続は次の操作から許可する。

操作が途中で失敗すると、実際に進んだフレーム数やボタンの解放を確認できない場合がある。確認できない状態を成功として返さず、エラーに含めて伝える。

### 5.3 標準入力の切断

標準入力が閉じたら、`handler.ts`は操作キューとCONTROL接続の終了処理を呼ぶ。キューは待機中の操作を失敗として終了させる。接続層はソケットを破棄して、実行中の応答待ちを解除する。`features`以下は`handler.ts`に依存しない。

## 6. 実装方針

`src/index.ts`と`src/control.ts`は新しい責務に沿って作り直す。`src/handler.ts`、`src/lib/operation-queue/index.ts`、`src/lib/tool/index.ts`、`src/features/tools/press-button/index.ts`を作成する。不要になった`src/server.ts`を削除する。`src/lib/socket-reader`は指定長を順に読み、余剰バイトを持ち越す機能を維持する。内部実装は必要に応じて作り直す。

実行入口を`src/handler.ts`へ変更するため、`package.json`の`bin`と`start`、利用手順、統合テストの起動パスを更新する。`press_button`の公開名、入力制限、コマンド順序、戻り値、失敗時のボタン解放は維持する。テストの構成は新しい責務に合わせて組み直す。

## 7. 検証方針

- MCPの初期化時にソケットが未起動でも応答でき、設定の欠落は起動時に検出できることを確認する。
- `press_button`の入力制限、コマンド順序、戻り値、失敗時のボタン解放を確認する。
- 操作キューの投入順、操作中のコマンドの非交錯、失敗後の後続操作、要求ごとの結果を確認する。
- `tools/list`がゲーム操作の応答待ちに妨げられないことを確認する。
- コマンドのエラー応答、接続断、タイムアウトを確認する。失敗した操作を再実行せず、次の操作で再接続することを確認する。
- 分割された応答と連続した応答を読み取れることを確認する。`CAPTURE`の画像本文も本文長に従って読み取り、本文中の改行を終端と誤認しないことを確認する。
- 標準入力の切断後、待機中と実行中の操作が終了し、ソケットが閉じることを確認する。
